## 1. 桌面设计原则（在 §2 六条之上补充）

移动端 §2 的六条（状态第一、流式顺滑、浅色优先、拇指操作、信息密度适中、🔴 安全可见）
在桌面端的调整：

1. **拇指操作 → 键盘优先**。核心动作都有快捷键，鼠标操作有 hover 与右键菜单兜底。
   「最小触控目标 48」在桌面**降到 28–32**（鼠标精度远高于拇指）——这是整个 token 体系
   在桌面端最重要的一处变化，照搬 48 会让界面显得松散、信息密度不足。
2. **同屏优先**。移动端因为屏幕窄，必须「列表 → push 详情」来回切页；桌面有横向空间，
   应当**列表与内容同屏**。这直接服务「随时切到电脑上接着干」的核心场景——不用导航就能看到
   「哪个会话在跑、哪个在等我审批」。
3. **密度优先于留白**。移动端 §4.1.1 的「留白充足（左右 20、区块间距 24+）」是为触控服务的；
   桌面收紧到区块间距 16–20，列表行高按内容给，追求「一屏看到更多」。
4. **不抢焦点**。桌面可以多窗口共存，任何通知/审批**不得抢走键盘焦点或把窗口拽到前台**
   （移动端没有这个问题，因为它就是唯一前台应用）。审批在非当前会话时用通知 + 侧栏角标提示。

## 2. 信息架构：从「底部 Tab + push」到「左栏 + 主区 + 可选右栏」

移动端 IA（§3）是 10 屏 + 2 浮层，底部 3 Tab + 全屏 push。桌面对应关系：

```
┌─ 未连接 ──────────────────────────────────────────────┐
│  ① 连接服务器（居中卡片，不再是全屏门禁）                 │
│     含桌面独有区块：「本机 daemon 发现」                  │
└──────────────────────┬────────────────────────────────┘
                       │ 连接成功
┌──────────────────────▼────────────────────────────────┐
│  左栏（240–400px，可拖拽调宽，常驻）                      │
│    ├─ 顶部：连接切换器（本机 / 其他电脑）+ 连接状态胶囊      │
│    ├─ Workspace 切换器                                   │
│    ├─ [+ 新建会话]（⌘N）                                 │
│    ├─ 会话列表（本 Workspace；按状态分桶，见 §6.2）          │
│    └─ 底部：⑤ 文件 / ⑦ 设置 入口  +  「N 个任务运行中」    │
│                      │                                │
│  主区（随左栏选择切换）  │                                │
│    ├─ ③ 聊天详情（默认）                                 │
│    ├─ ⑤ 文件（改动 / 全部文件）                          │
│    └─ ⑦ 设置                                          │
│                                                       │
│  右栏（可选、可折叠，320px）——桌面独有增益                 │
│    └─ 本会话上下文：改动文件 / 待办 / 已授权工具            │
└───────────────────────────────────────────────────────┘

浮层/模态（不再有「底部 Sheet」，一律居中模态）：
  Ⓟ 权限审批  ④ 新建会话  ⑧⑨⑩ 工作区管理 / 目录选择器 / 会话权限
```

**为什么是「左栏 + 主区」，而不是 VSCode 式「活动栏 + 列表栏 + 内容」三栏常驻**：
本产品的核心动作是**读一条长回复 + 审批一个命令**，聊天需要宽度；再塞一个活动栏会让聊天变窄。
「文件」「设置」是低频入口，占满主区即可，不值得常驻一栏。会话列表常驻左栏是收益最高的那一个
（它承担「哪个会话在跑 / 在等我」的状态感知）。

**右栏是可选增强（🟡，M3）**，不阻塞 M1：移动端把「改动文件 / 待办」藏在别的 Tab 里，
桌面可以把它并到聊天旁边，边看回复边看改了哪些文件。

**移动端 → 桌面 导航映射**：

| 移动端 | 桌面 |
|---|---|
| 底部 Tab Bar（会话/文件/设置） | 左栏底部两个入口（文件/设置）；会话列表直接在左栏 |
| 全屏 push 详情页 | 主区内容切换（同屏，无 push 动画） |
| 底部 Sheet（新建会话） | 居中模态对话框 |
| 全屏浮层（权限审批） | 居中模态对话框（不可点外部关闭） |
| FAB「+」 | 左栏顶部「新建会话」按钮 + `⌘N` |
| 顶部栏 + 状态栏 inset | 自绘标题栏，**无 inset 概念**（见 §3） |

## 3. 窗口与布局规格

| 项 | 值 |
|---|---|
| 默认窗口 | 1280 × 800 |
| 最小窗口 | 960 × 640（低于此左栏可自动折叠为图标条） |
| 左栏宽度 | 默认 300，可拖拽 240–400，宽度持久化 |
| 右栏宽度 | 默认 320，可折叠（🟡 M3） |
| 聊天正文 | **最大宽度 760 居中**——超宽屏上不要让一行文字横跨 2000px |
| 代码/工具输出 | 不限宽，横向可滚动（宁可滚，不要折行破坏对齐） |
| 标题栏 | 自绘（`titleBarStyle: 'hiddenInset'` on macOS，`frame: false` + 自绘按钮 on Win/Linux）。左侧为 macOS 交通灯留 78px |
| 缩放 | `⌘/Ctrl +` `-` `0` 支持界面缩放（90%–150%） |
| 主题 | 浅色 / 深色 / 跟随系统，三态切换（移动端只有跟随系统 + 手动，桌面要给显式三态） |
| 高 DPI | 图标用矢量，`@2x` 位图仅在必要处 |

**标题栏内容**（自绘，整条可拖拽移动窗口）：左侧产品名 + 连接状态胶囊；右侧留窗口控制按钮。
把连接胶囊放进标题栏，是移动端「各页顶栏都放一个」的桌面收敛——桌面只有一个窗口外壳，
全局状态只该有一个位置。

## 4. Design Tokens 的桌面适配

**色彩：完全沿用 `docs/ui/shared/design-principles.md` §4.1，不新增、不改值。**
品牌渐变、elevation 三级、身份色体系照搬。唯一差异是**用法**而非取值：

- 深色主题在桌面是**真正的一等公民**（开发者桌面常年深色）。移动端说「浅色优先」，
  桌面端改为「跟随系统，且两套都要精心调」。
- 浅色主题在桌面上，层次更多靠 **1px `border` + 极轻阴影**，而不是移动端那种较重的
  `elevation-2`（桌面窗口在显示器上若用重阴影会显脏）。

**字号与密度（桌面列）**：

| 语义角色 | 移动端 | 桌面 | 说明 |
|---|---|---|---|
| 页面标题 | 20 | 16 | 桌面窗口标题/面板标题不需要 20 |
| 列表标题 / 卡片标题 | 16 | 14 | 左栏会话项 |
| 正文 | 14 | 14 | **不变**（14 是桌面阅读舒适的甜点） |
| 辅助说明 | 12 | 12 | 不变 |
| 代码 / 路径 / token / 命令 | 13 | 12.5–13 | 等宽 |
| — | （新增） | 11 | 元信息（相对时间、徽章、快捷键提示） |

**间距与圆角**：

| Token | 移动端 | 桌面 |
|---|---|---|
| 基准网格 | 4 | 4（不变） |
| 区块间距 | 24+ | 16–20 |
| 卡片圆角 | 12 | 8–10（桌面更紧凑） |
| 消息气泡圆角 | 16 | 12 |
| 模态圆角 | 24（Sheet 顶部） | 12（居中模态四角） |
| 最小点击目标 | 48 | **28–32** |

**字体族（桌面明确指定，不用「系统默认」这种移动端写法）**：

- UI：`-apple-system, "Segoe UI", Inter, "Noto Sans SC", sans-serif`
- 等宽：`"JetBrains Mono", "SF Mono", "Cascadia Code", Menlo, Consolas, monospace`

**滚动条**：细的 overlay 滚动条（宽 10，hover 加深），跟随主题；**不要**用浏览器默认的粗滚动条。

## 7. 桌面独有交互

### 7.1 键盘快捷键（全部可配置，此处为默认）

| 快捷键 | 动作 |
|---|---|
| `⌘N` | 新建会话 |
| `⌘K` | **命令面板**（会话跳转 + 工作区切换 + 动作；桌面最常用的导航方式） |
| `⌘B` | 切换左栏显隐 |
| `⌘1` / `⌘2` | 切到 会话 / 文件 |
| `⌘,` | 设置 |
| `⌘R` | 刷新当前列表 |
| `Enter` / `Shift+Enter` | 发送 / 换行（可改为 `⌘Enter` 发送） |
| `⌘L` | 聚焦输入框 |
| `⌘.` 或 `Esc`（输入框内） | 停止当前 run |
| `Shift + Tab` | 循环切换会话的权限模式（`ask` → `acceptEdits` → `bypass`；`bypass` 需二次确认） |
| `⌘⏎` / `⌘⌫` | 审批卡片内：允许 / 拒绝 |
| `⌘⇧E` | 展开/折叠全部工具组（§6.3） |
| `⌘⇧[` / `⌘⇧]` | 上一个 / 下一个会话 |
| `⌘P` | 搜索文件（🟡 M3） |
| `⌘F` | 文件内容 / 会话内搜索 |
| `⌘+/−/0` | 界面缩放 |
| `?` | 快捷键帮助 |

> **`⌘K` 定为命令面板而不是「会话快速切换」**——这是与 paseo 对齐后的修正（paseo：`⌘K` 命令面板、
> `⌘P` 搜文件）。会话快速切换并入命令面板即可，不必占一个独立快捷键；`⌘K` = 命令面板已是开发者
> 工具的通行约定，另立一套反而要重新学。

> **实现形态参考 paseo**：快捷键定义是**一个数据数组**（`{id, action, combo, when, help}`），
> 匹配/派发、帮助面板都由它生成，用户自定义**按 `id` 存**（所以 id 必须稳定，改 id 等于丢掉用户的
> 自定义）。`when` 支持 `mac / 可编辑区 / 输入框内 / 模态打开` 等条件门控。别把它写成一堆散在
> 组件里的 `onKeyDown`——那样做不了自定义、也做不了帮助面板。

`⌘K` 是本设计中**唯一需要新增组件**的快捷键（命令面板/快速切换），但它是桌面高频操作，
建议 M2 做。

### 7.2 鼠标与右键

- **hover 取代长按**：所有移动端「长按弹出操作」的地方，桌面一律改为 hover 露出按钮
  （会话项、消息、文件树）。长按在桌面上是反常交互，不要保留。
- **右键菜单**是桌面的一等信息通道，移动端无对应。至少覆盖：会话项、消息、工具卡片、文件树。
- **不要**保留「左滑删除」——桌面无触摸滑动语义。

### 7.3 多窗口（🟡 M3）

桌面独有的最大结构性增益。两种形态：
1. **同 daemon 多窗口**：每个窗口一个会话，可并排看两个 agent 跑（双显示器场景）。
2. 数据共享：多窗口共享同一主进程（`stream:event` 广播到所有窗口），token 与连接单例。

实现上主进程本就持有流，多窗口只是多一个 `webContents.send` 目标，边际成本低。
但会引入「哪个窗口算『正在看』」的判定（影响通知抑制，见 §7.4），所以放 M3。

### 7.4 系统通知与托盘（对应移动端 §7.7）

**触发条件与抑制规则沿用**（审批请求 / 终局事件；仅当「人没在看这个会话」时弹；
审批已决要撤掉那条「需要审批」）。

通知的数据源是**本客户端自己持有的流**：它发起的那条 run（`/api/chat` 的响应）以及它打开着的会话
的 run 流。产品模型是「谁发起、谁审批」（方案已定 20），所以**不需要**去订阅别的设备发起的 run。

桌面差异：

- 抑制判定从「应用前台 + 当前可见会话」改为「**窗口聚焦 + 该会话在任一同屏窗口可见**」。
  多窗口下只要有一个窗口正显示该会话，就不打扰。
- **审批已决撤掉通知**在桌面上更容易实现（`Notification.close()`），必须做，否则通知中心会堆积。
- **通知 id 按 `permissionId` 派生，不要按 `sessionId`**。Android 是按 `sessionId.hashCode()`
  取的 id，后果是**同一会话里并发多个 run 时通知会互相覆盖**（一条「任务完成」能把一条仍在等待的
  审批通知盖掉）。桌面上按 `permissionId` 派生即可避免。
- **通知不带「允许/拒绝」按钮**，只做「点击进入会话」——沿用 Android 的取舍。🔴 在通知栏直接放行
  一个 `Bash` 命令的误触风险太高，多一下点击是值得的。
- **托盘**（桌面独有）：常驻托盘图标，显示运行中任务数；菜单含
  `打开主窗口` / `N 个任务运行中 →（可跳转）` / `退出`。
  **关闭窗口 ≠ 退出应用**（托盘继续常驻，任务照跑）——这是桌面约定，需要在设置里给出
  「关闭窗口时：最小化到托盘 / 退出应用」的显式选择，不能默默替用户决定。
  > 与 §7.5 的关系：托盘负责**让 app 活着**（这样才有通知来源），§7.5 负责**退出时 daemon 的去留**。
  > 两者是同一件事的两面——「我离开电脑」这个场景要求**两层都别断**。
- 首次运行时申请通知权限的时机沿用移动端（**真的有事要跑时才申请**，不要启动就弹）。

### 7.5 退出应用时的 daemon 确认（桌面独有）

「关闭窗口」与「退出应用」是两件事（移动端没有窗口概念，所以无此问题）：

- **关闭窗口** → 默认最小化到托盘，任务照跑，**不问、不碰 daemon**。
- **退出应用**（托盘菜单「退出」/ `⌘Q`）→ 才决定 daemon 去留。

只在 **daemon 是本客户端 spawn 的**时候才问；附着来的（systemd 等）不问也不停。

对话框形态（首次弹，勾选后走设置项）：

```
┌─────────────────────────────────────────────────┐
│  退出 paboot？                                  │
│                                                 │
│  本机 daemon 正在运行，且有 2 个任务在跑。          │
│                                                 │
│  退出应用时：                                     │
│    ● 保留 daemon（手机仍可连接，任务继续跑）        │
│    ○ 同时停止 daemon（手机将断开，任务会被中断）    │
│                                                 │
│  ☐ 记住我的选择                                   │
│                    [ 取消 ]  [ 退出 ]            │
└─────────────────────────────────────────────────┘
```

**默认选中哪一项，取决于「是否可能有别人依赖它」**（技术方案 §5）：

| 条件 | 默认 |
|---|---|
| 手机访问**开着**，或**有运行中的任务** | **保留 daemon** |
| 两者都不成立（仅本机 loopback + 无任务） | **同时停止 daemon** |

设计理由：产品的一句话是「任务始终在电脑上执行，手机只是遥控器」，移动端文档也承诺了
「手机断连不影响任务」。**对称的承诺是「关掉桌面端也不影响任务」**——固定默认「停止」会让
这个承诺单向失效。而在「没人依赖它」时默认停止毫无副作用（loopback 无任务，本来没人能用），
所以两种取向并不真的冲突。

文案要点：**必须写出「会有几个任务被中断」**，否则用户不知道自己正在杀掉跑一半的 agent。
「记住我的选择」勾上后，设置页「退出应用时」收敛为三态：`保留 daemon` / `同时停止` / `每次询问`。

### 7.6 深链

移动端用通知 → 透明 `DeepLinkActivity` 跳到会话（因为 Android 12+ 的限制）。
桌面无此限制：通知/托盘的跳转直接在主进程处理（`mainWindow.show()` + 切到目标会话），
不需要中间 Activity 那层 trampoline。外部深链（`paboot://session/<id>`）也收敛到同一处理器。

## 9. 已定与待定

**已定**（据此推进，不再讨论）：
- 深色主题**默认跟随系统**（§4）——移动端是「浅色优先」，桌面按下开发者工具惯例改。
- 🔴 审批**不抢焦点**：非当前会话的请求走通知 + 左栏角标，超时自动拒绝兜底（§6.5）。
- 🔴 审批**按危险度分流**：`Bash` / Codex `Permissions` 用模态，`Write` / `Edit` / `MultiEdit` /
  MCP 用内联置顶卡片（§6.5 末尾）。分流依据是 `toolName` 白名单，不去解析 `toolInput`。
- 🔴 **多端并发时审批在两端各自弹出**，谁先答谁生效、另一端的弹窗自动消失（§6.5 末尾的多端小节）。
  **不做客户端互斥**（「谁发起谁审批」会引入需要同步的协调状态，且丢掉「手机上也能处理」的价值）。
  「允许全部」文案要写明**跨设备生效**。
- 🔴 **不做跨端审批通知**（方案已定 20）：产品模型是「谁发起、谁审批」。桌面端**不订阅别的设备
  发起的 run 的内容**；左栏的运行中标记靠常规轮询，要接着看就进那个会话（进去时附着 + 回放）。
  通知只覆盖本客户端自己发起 / 打开着的 run（§7.4）。
- **「新建会话」的最小形态（方式 A + Agent 选择器）属于 M1**（§6.4、§8）——没有它 M1 不可用，
  且 Agent 选择器正是「在一个端上同时用 claude 和 codex」这个初衷的落点。
- **桌面端可连其他电脑上的 daemon**，左栏顶部放**连接切换器**（§2、§6.1）；远程只读，不可管进程。
- 🔴 **连非 loopback 的 http 地址时必须有加密警告**（§6.1）。
- 🔴 **退出确认采用 §7.5 的自适应默认**（有手机访问或运行中任务 → 默认保留；都没有 → 默认停止）。
- **左栏按状态分桶**（§6.2）——M1 至少做「等待我处理 / 运行中」两桶，其余桶 M2 补齐。
- **连续工具调用折叠成一组**（§6.3）属 **M1**：它决定消息列表的结构，和虚拟化一样，
  事后加要重构渲染层。
- **快捷键做成一个数据数组 + 按 id 存用户自定义**（§7.1）属 **M1**。
- `⌘K` = **命令面板**（含会话快速切换），M2（§7.1）。
- 右栏面板先做**改动文件**（§2）。
- 多窗口**共享主进程连接**，不各自建连（§7.3）。
- 只把 token 表与 §4.5 映射表回填 `docs/ui/`，其余桌面规范留在本文件（§0）。

**仍未定**：
- **关闭窗口行为**：默认「最小化到托盘」还是「退出」？推荐最小化到托盘 + 设置项可改，
  且首次关闭时提示一次，不能默默常驻（§7.4）。M2 做托盘时定。
- **多机同屏什么时候做**（M3+）：M1 只做一次连一个 + 切换入口；真做多机时还要定
  「切走那台机器的会话是否仍留在左栏」。
- **托盘是否真做**：paseo（同类成熟产品）全仓库没有 `Tray`，它把「常驻」交给 CLI/headless daemon。
  paboot 的常驻是 systemd，所以托盘对我们仍有意义（关窗后任务继续跑），但值得在 M2 重新确认
  一次是否真需要——托盘会引入「关窗≠退出」的认知负担。
