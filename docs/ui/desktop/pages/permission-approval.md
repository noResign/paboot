# Ⓟ 权限审批（Permission Approval）— 桌面

> 索引与全局规范见 [../design.md](../design.md)。移动端原页：
> `docs/ui/mobile/pages/permission-approval.md`——**按工具类型的渲染完全沿用，本文件只写桌面差异**。

### 6.5 Ⓟ 权限审批（Permission Approval）🔴 安全边界

**目的**：agent 想执行需要审批的工具时暂停运行，由用户允许/拒绝。**这是本产品的安全边界。**

**🔴 已定：按危险度分流**（技术方案已定 17）。移动端一律全屏浮层；桌面端分两条路：

| 工具 | 桌面形态 | 理由 |
|---|---|---|
| `Bash`（尤其含写/网络）、`TerminalInput`、Codex `Permissions` | **居中模态，宽 560，不可点外部关闭** | 最高风险，必须阻塞、不可错过、不易误触 |
| `Write` / `Edit` / `MultiEdit` / MCP 工具 | **内联置顶卡片**（吸顶在消息流顶部，多个 pending 自然堆叠） | 日常编辑不打断阅读；多并发 run 时模态互相打架 |

- **分流依据是 `toolName` 白名单**，**不去解析 `toolInput`**——解析命令里有没有写操作既不可靠
  也说不清。将来 Codex 新增 `TerminalInput` 也归模态。
- 两路**共用**左栏 `⚠ N` 角标（§6.2）与系统通知（§7.4）这两个保险，**不因为分流少给一个**。

#### 内联置顶卡片（`Write`/`Edit`/MCP 一路）

- **吸顶**在消息流顶部，不随滚动消失；多个 pending 顺序堆叠；卡片内含与模态同样的按钮组。
- 这是「不把安全降级」——移动端规格里本来就有通知 + 未读逻辑，这里只是把「阻塞」换成
  「提醒 + 角标 + 通知」。

#### 居中模态（`Bash`/`Permissions` 一路）

四条桌面差异（相对移动端的全屏浮层）：

1. **居中，宽 560，不可点外部关闭**（语义同移动端）。
2. **队列化**：daemon 支持并发 run，可能同时来多个请求。模态一次展示一个，标题右侧 `1 / 3`，
   底部给「下一个」；**不允许「全部允许」跨请求批量提交**——那等于一次点击放行多个未知命令。
   每个请求独立作答。
3. **非当前会话的请求不抢焦点**：若 `permission_request` 属于**非当前打开的会话**，不弹模态
   （弹了会打断当前工作），改为**系统通知 + 左栏该会话的 `⚠ N` 角标**；用户切过去时才弹。
   🔴 这是桌面相对移动端的**降级打断**。移动端没这个问题，因为它是唯一前台应用。
4. 按钮加**快捷键提示**（`⌘⏎` 允许 / `⌘⌫` 拒绝），但**默认焦点放在「拒绝」之外**、
   `Esc` **不关闭**模态（改为聚焦「拒绝」）——🔴 避免回车误放行。
   长命令给「复制命令」按钮（移动端只能长按）。

**其余完全沿用移动端**：按工具类型渲染（`Bash` 全文等宽可滚动、`Write` 路径+内容、
`Edit` 路径+diff、Codex `Permissions` 的路径/网络/`special` 中文标签、其他通用 JSON）、
警示图标 + 「⟨Agent⟩ 请求执行」、安全提示小字、`超时未处理将自动拒绝`（**不写死 120 秒**）、
三个按钮（允许 / 允许全部（本 Session）/ 拒绝 + 理由输入）、以及「允许全部」的作用域说明与
Codex `Permissions` 的例外文案。

#### 🔴 多端并发时审批会同时出现在两台设备上

`permission_request` 是**广播给该 run 的所有订阅者**，不是只发给发起者——所以**桌面和手机若都
订阅了同一条 run，两端会各弹一个审批 UI，是同一个 `permissionId`**。（若手机没打开过那个会话，
它不订阅，也就不会弹——见「谁发起、谁审批」，技术方案已定 20。）

对设计的三点要求：

1. **文案要写明作用域是跨设备的**。「允许全部」的说明要从「本 Session 后续所有 Bash」改成
   **「本会话后续所有 `Bash`（其他设备看这个会话时同样免问）」**——grant 存在 daemon 上、
   按 Session + toolName 记账，一端点了另一端也生效。用户按「允许全部」时的默认预期往往只是
   「这台设备」。撤销只能在 §6.9 的 ⑩ 里撤，且撤不回已批准的操作。
2. **不要假设「是我答的」**：作答后 UI 必须以**服务端回播的真实 status** 为准，而不是以自己点的
   按钮为准——另一端可能已经先答了（幂等返回，或 `allow_all` 撞 409）。弹窗关闭的触发条件是
   「收到同一 `permissionId` 的非 `pending` 帧」，**不是**「我的 POST 返回 200」。
3. **另一端的弹窗要能自动消失**，且消失时**不要弹「已处理」的 toast**——用户可能根本没看到那个
   请求就没了。最多在消息流里留一条轻提示（🟡）。

> 反过来说，**不要**为了「避免重复弹窗」去做客户端互斥（比如「谁发起谁审批」）。那会引入一个
> 需要同步的协调状态；而「两端都弹、谁先谁生效、自动收敛」在分布式下更简单也更健壮——少了一台
> 设备在线与否的分支。手机上能直接处理审批，本身就是这个产品的价值。

### 6.5.1 Ⓟ′ 需要你的回答（User Input）🔴

**完全沿用移动端**（`questions` / `form` / `url` / `unsupported` 四种渲染、**无「允许全部」**、
答案只回给提供方且**不写入历史/不进 SSE**、未处理按超时拒绝、错误就地显示含 `bad_response` 的
字段细节）。桌面差异：

- `url` 类型的「打开链接」走**系统默认浏览器**（`shell.openExternal`），并沿用「打开链接不等于
  批准」的说明。
- 形态：按危险度分流表走 `Permissions` 那一路（**模态**）——它虽然没有「允许全部」，但同样会
  阻塞 run，不该被内联卡片稀释。
