> 连远端，从不管理进程。本页是桌面端「和 daemon 同机」这件事带来的新页。

### 6.6 ⑥ 本机 daemon 管理（Daemon）🖥 桌面独有

**目的**：让用户看清「本机 daemon 现在什么状态、谁启动的、怎么管它」，并能对它启停 / 看日志。

> **口径（2026-10 修订）**：数据目录固定 `~/.paboot`，daemon 自己用 `paboot.lock` 保证同一目录
> 只有一台。所以「本机 daemon」只有一台，**启停对它开放，不论是谁启动的**；「谁启动的」
> （本应用 / systemd / 手动）只决定**怎么启停**与怎么展示，不再是能不能管的闸门。
> 这一条推翻了早先「只有本应用 spawn 的才可管」的设计——用户反馈：桌面端重启后，上次留下的
> daemon 既管不了也停不掉，非开发者只能去 `kill`。

**入口**：设置页的「本机 daemon」区块 → 或标题栏下方 daemon 状态条的点击（§5 组件表）。

**关键元素**（主区整页）：

```
本机 daemon
────────────────────────────────────────────────────────
状态      ● 运行中（本应用托管）
版本      v1.8.0
地址      127.0.0.1:4780
工作区    ~/Projects
数据目录  ~/.paboot
手机访问  ○ 关闭（仅本机）          [ 开启… ]

[ 重启 ]  [ 停止 ]  [ 复制 token ]  [ 改 token ]
────────────────────────────────────────────────────────
日志  ▾                              [ 自动滚动 ] [ 清空 ]
[2026-10-08T00:18:54] INFO  paboot 1.8.0
[2026-10-08T00:18:54] INFO  bound to 127.0.0.1:4780
[2026-10-08T00:18:55] INFO  claude: v2.x (authenticated)
```

**🔴 能力按「谁在管」分档**（技术方案 §4 的表）：

| 能力 | 本应用 spawn 的 | systemd 托管 | 手动起的 | 远程 |
|---|---|---|---|---|
| 看状态 / 版本 / 地址 / PID / 归属 / 日志 | ✅ | ✅ | ✅ | 只读状态 |
| 停止 / 重启 | ✅ | ✅ 走 `systemctl --user stop` | ✅ 按 pid 发 SIGTERM | ❌ |
| 启动 | ✅ spawn | ✅ `systemctl --user start`（工作目录/端口由单元决定） | ✅ spawn | ❌ |
| 手机访问开关 | ✅ | ❌ 由单元决定，只读显示绑定 | ❌ | ❌ |
| 改 token | ✅ 写文件 + 重启 | ✅ 写文件 + `systemctl --user` 重启 | ⚠️ 只写文件，交给用户自己重启 | ❌ |

- **会 shell out `systemctl`**（推翻早先「那是部署流水线的活，会打架」的判断）：只有走
  `systemctl`，单元状态才和实际一致。但**只在确认该单元的 MainPID 就是当前那台 daemon 时**才走
  （`systemctl --user show -p MainPID`），否则退回按 pid 发信号——避免「装了单元、但 daemon 是
  手动起的」被误当成 systemd 的去停。
- **不需要 sudo，也不能用 sudo**：走的是 `systemctl --user`（用户级单元，通往本用户的 systemd 实例）；
  前提是 user session bus 在，桌面端会兜底补 `XDG_RUNTIME_DIR` / `DBUS_SESSION_BUS_ADDRESS`。
- **失败必须看得见**：`systemctl` 的 stderr 会带进错误文案；**停止失败也回一个错误**给界面
  （否则唯一症状是「状态还写着运行中」，看着像按钮坏了）。
- 手动起的 daemon 我们**不知道怎么把它启回来**（命令/参数只有用户知道），所以「改 token」只写文件
  不重启，并如实告知；停止/启动仍然可用（启动等于按表单 spawn 一台新的）。
- **上次运行留下的那台**：启动命令（command/args/workspace/port/host）随身份一起**持久化**，
  所以重启桌面端后它仍可被重启/「改 token 顺带重启」——UI 用 `status.restartable` 区分。
- 远程 daemon 这一页退化成**只读的状态卡**（版本/地址/延迟），不给任何按钮。

**「手机访问」开关** = 托管子进程的 `--host`（`127.0.0.1` ↔ `0.0.0.0`），🔴 **安全相关**：

- 开启时是**显式确认**（模态 + 风险说明 + 展示局域网地址与 token 的二维码/复制），
  **不是静默切换**。理由：绑 `0.0.0.0` 等于在局域网里开了一个「单个静态 token 背后的、
  带 shell 权限的 RCE 端点」。
- 关闭时也要说清后果：「手机将无法连接」。
- 非托管 daemon 上这一行只读显示探测到的绑定（本机 systemd 是 `0.0.0.0`，所以显示「开放中」）。

**「改 token」** = 重写 `<data-dir>/token` 并**重启托管 daemon**——daemon 只在启动时读一次 token，
不重启就不生效，所以「改了没用」的错觉必须靠重启避免：

- 对**能重启的** daemon 开放：本应用启动的、systemd 托管的（重启走 `systemctl --user`）。
  手动起的只写文件、不重启（见上表），并在 UI 里说明「需要你自己重启才生效」。
- 输入留空 = 随机生成 32 字节 hex；也可粘贴自定义值（8–512 个可见字符、不含空格）。
- 🔴 改 token **等于换掉远程 shell 的钥匙**：所有已连接客户端（手机、别的电脑）立刻失效，必须重新输入新 token。
  所以要有**二次确认**（重启还会中断正在跑的任务），改完把**新 token 显示出来**（可复制）——否则用户拿不到刚设的凭据。

**日志面板**：等宽、跟随主题、`INFO/WARN/ERROR` 按语义着色（`text-secondary`/`warning`/`error`）、
主进程 5000 行环形缓冲、按 100ms 批量推给渲染层、可复制、可导出（🟡）。
**绝不把原始栈抛给用户**——supervisor 捕获的 stderr 走人话提示（技术方案 §2）。

**spawn 相关**（M4；但设计上现在就要留位）：

- 首次「启动一个本机 daemon」要**先选工作目录**——`--workspace` 在首次启动就锁定了默认工作区
  且**不可删除**，而它是 agent 的写入边界（技术方案已定 23）。选完再问「手机访问」。
- **端口冲突**不在这页做文章：走 §6.1 连接页的发现分支（更早暴露），这页只显示结果。

**状态**：
- 未运行 / 运行中（附 **PID** 与**归属**：本应用启动 / systemd 托管 / 手动启动） / 启动中
  （显示就绪轮询进度） / 启动失败（人话错误 + 「查看日志」）。
- 版本与本 app 内置的 daemon 不一致时（技术方案「版本漂移」）：给一条提示 + 「重启以使用内置版本」，
  **只在托管 daemon 上给**——附着的外部 daemon 永不提示重启。
